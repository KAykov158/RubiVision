# Category 03: scramble contracts and architecture

**Status:** Phases 01–06 contracts, generation/validation, timer lifecycle, provenance persistence, and saved history are implemented locally. The scramble-derived viewer and daily challenges remain open. The Phase 01 decision record below retains its original forward-looking language for traceability.

## Authority and existing boundaries

The Category 03 specification and prompt 01 require event-specific generation, exact notation, provenance, and an immutable timer association. Master decisions 11 and 17 override older IndexedDB and offline-outbox directions: Supabase PostgreSQL is the only persistent application database. Guest timing remains available; an unsaved solve remains only in tab memory with manual retry or export.

Reuse `PuzzleType` (`222` through `777`), `Scramble`, `ScrambleService`, `ServiceResult`, and the current timer completion and Supabase repository contracts. The existing timer captures the scramble, puzzle, session, owner when signed in, and solve UUID when timing starts. At the Phase 01 baseline, the production generator returned `UNSUPPORTED` and no event-specific parser existed.

## Contract decisions

1. A scramble's UUID, puzzle code, exact displayed notation, generator version, and UTC creation time are one snapshot. `Scramble` fields are TypeScript `readonly`; this does not freeze an object at runtime. Phase 04 must ensure the displayed and saved snapshots cannot diverge during a run or retry.
2. `generatorProvider` and `generationMethod` (`RANDOM_STATE` or `RANDOM_MOVE`) are optional additive fields so existing fixtures and the current database adapter remain compatible. A verified Phase 02 provider must supply truthful metadata for each supported event. `generatorVersion` already exists. Do not assert a method for any event until its provider behavior is verified. No seed field is added without reproducible provider support.
3. Validation must occur at the event-specific generator boundary before a scramble becomes ready or saveable. A future validator should return `ServiceResult<void>`; `generate` continues to return `ServiceResult<Scramble>`. Use `success` only after validation, `error/INVALID_INPUT` for invalid notation or puzzle mismatch, `unavailable/UNSUPPORTED` for an unsupported event, and `error/CANCELLED` for an aborted request. Other provider failures must return an error, never the last scramble as success. Phase 02 will choose the parser and implement this behavior; no competing result type or unimplemented validation method is added now.
4. `generate(puzzle, options?)` accepts an optional `AbortSignal` without changing existing callers. A future coordinator must identify each request, ignore results for an obsolete puzzle/request, and cancel where supported. Repeated incidental requests for the same pending puzzle may share work; an explicit regenerate supersedes the previous request. A duplicate generated scramble must not silently replace the current one. Phase 02 must choose and test a bounded retry limit after provider behavior is known.
5. Generation must run client-side without depending on Supabase configuration, Auth, or a cloud request. The current `AppProviders` wiring does not meet this yet; Phase 02 must provide the generator to guests and handle offline/provider errors without blocking the timer.
6. The timer start boundary is the existing `TimerCompletionProvider.startTimer`. From then through stop, save failure, and retry, the scramble ID, puzzle, notation, provenance, session selection, and solve UUID must remain associated with that run. The current provider stores the `Scramble` object by reference; Phase 04 must harden runtime snapshot and display locking. A new scramble becomes eligible only after the prior solve is finalized or explicitly discarded. Current post-save generation leaves the previous result available while a new request runs; Phase 03/04 must close that reuse window.

## Persistence and history

The existing `scrambles` table stores owner, puzzle, notation, `generator_version`, and time. A trigger makes rows immutable; `solves` links by owner/puzzle and limits one solve per scramble. Current `ScrambleRepository.save` writes only those existing columns and drops the new optional metadata. **Provider and method are not durably persisted in Phase 01.** Phase 05 should decide and test an additive migration and TypeScript mapping for separate provider/method fields before claiming that provenance survives reload. No new basic-scrambles table is needed.

For Category 03 history, a *saved* scramble means one linked to a server-confirmed solve. Generated-but-unused scrambles are ephemeral in memory; a successful scramble insert followed by a failed solve insert is not a confirmed history item. This definition keeps history truthful with the current sequential save path. Phase 06 must use an owner-scoped, bounded query and distinguish ephemeral entries. A later decision may consider an atomic save if partial inserts cause unacceptable behavior.

The optional scramble-derived viewer and full daily challenge remain separate later slices. Practice generation must not be replaced by a challenge implicitly. A viewer may show only the mathematically derived state of a known scramble, never a camera-observed physical state.

## Phase 01 handoff to Phase 02

- Verify a browser-compatible provider's API, 2x2–7x7 event coverage, actual random-state/random-move methods, license, and performance before selecting it. No library is selected here.
- Implement event-specific parsing, runtime validation, request coordination, cancellation, duplicate policy, and focused tests.
- Keep the provider independent of Supabase and preserve existing signed-out timer and volatile-save behavior.
- Carry the metadata migration requirement into Phase 05; do not treat optional in-memory fields as persisted evidence.

## Phase 02 implemented generator and validation

The client uses `cubing` **0.66.1**, pinned in `apps/web/package.json`, through its public `cubing/scramble` export `randomScrambleForEvent(eventID): Promise<Alg>`. The package declares `MPL-2.0 OR GPL-3.0-or-later`; the app uses the unmodified library under the MPL option. Preserve the package's license notice and review distribution obligations before release. Evidence: [official scramble guide](https://js.cubing.net/cubing/scramble/), [official compatibility notes](https://github.com/cubing/cubing.js/issues/323), npm package metadata, and the installed 0.66.1 package exports and `wcaEvents` metadata. These are unofficial practice scrambles; the provider explicitly says to use the official scramble program for WCA competitions. No WCA certification or cryptographic randomness claim is made.

`createScrambleService` returns the provider's `Alg.toString()` text unchanged, with a new UUID, UTC timestamp, provider name, pinned version, and method. `validateScramble` uses `cubing/alg` parsing plus a bounded event-specific move check: only face turns, or 2-layer wide turns on 4x4–7x7, or 3-layer wide turns on 6x6–7x7. It rejects slices, rotations, grouping, comments, malformed suffixes, excess layer widths, more than the event's token cap, and text over 4096 characters. This validates syntax and puzzle compatibility; it does not prove state distribution, scramble quality, or physical cube state. Exact provider text is retained, including whitespace.

The provider runs generation in its own worker and does not offer an abort parameter on `randomScrambleForEvent`. The service checks `AbortSignal` before work and discards completions after abort or a newer request; cancellation does **not** stop an in-progress worker job. Provider calls are serialized, and superseded requests waiting in the queue skip generation. The current timer page also aborts/ignores obsolete requests on effect cleanup and keys displayed results to puzzle and post-save request identity. Cubing's default same-event prefetch remains enabled. Repeated output matching the previous successful scramble for the same puzzle is retried at most twice, then reported as `CONFLICT`; provider/validation failures never return an old scramble. Generation remains in memory and makes no Supabase request.

The `AppServicesProvider` supplies this generator even when Supabase is not configured, while keeping the overall cloud service state unavailable and exposing no solve or session repository. Configured Supabase services use the same client-side generator. The timer can therefore display a scramble for signed-out users and during a cloud outage; saved solves still require Supabase confirmation.

The provider requires modern ES2022 modules and workers. Vite emits ES module workers. Its build also disables Vite module preloading and uses an entry-aware `cubing` chunk group: without this, the generated worker imports the app entry chunk and throws `document is not defined`. The production build succeeds and emits lazy scramble/worker/WASM assets, including a roughly 671 kB uncompressed WASM chunk. A Chromium preview smoke check showed a ready scramble for all six puzzle sizes with no page errors; representative-device latency and other browsers remain unmeasured. The app bundle still triggers Vite's >500 kB chunk warning.

## Phase 03 puzzle selection and scramble UI

The timer page reuses its native puzzle selector and client-side generator. It offers exactly 222–777 with readable 2×2–7×7 labels. Every generation request is keyed by selected puzzle and the post-save solve identity, plus an explicit regeneration counter. Changing puzzle, requesting a new scramble, or completing a save makes the old result ineligible for display or timer start immediately. Effect cleanup aborts the request where supported and ignores late completions. The service's bounded duplicate policy remains the only duplicate handling.

The scramble card exposes generating, ready, failed, and unavailable states through status announcements. A failed request offers Retry; a ready scramble offers Copy Scramble and New Scramble. Copy writes the exact service notation through the Clipboard API and reports success or denial without a fallback write. The notation preserves whitespace and wraps on small viewports. Guests continue to use the local generator without Supabase configuration.

The page blocks the timer unless the current puzzle has a matching ready scramble. Puzzle selection and regeneration are locked while holding, armed, running, or while an unsaved completion blocks another run. The displayed result is also hidden while a replacement request is pending. These UI guards prevent a known missing, failed, pending, or wrong-puzzle scramble from starting a run. Phase 04 adds runtime snapshot locking in `TimerCompletionProvider`. Phase 05 must persist provider and method metadata with an additive schema change before claiming provenance survives reload.

## Phase 04 immutable timer snapshot and solve association

`TimerCompletionProvider` is mounted above the application routes, so its active run and pending save survive route-level timer-page unmounts. On the timer start boundary, after the existing hold/arm interaction and page-level ready/puzzle checks, the provider validates the scramble against the run puzzle, copies its identity, exact notation, version, timestamp, and optional provenance fields, then freezes that copy and the `ActiveTimerRun`. The completion path makes a second frozen copy of the captured scramble and completion. The page renders the provider's captured snapshot during an active run and while a completion remains unsaved; page-local generation state cannot replace it.

The solve uses the captured puzzle and scramble ID. Scramble insertion receives the same captured scramble object, while solve insertion receives the same solve UUID and captured scramble ID. Retry reuses the pending completion without generating a scramble. Existing repository uniqueness checks make repeated insertion of the same scramble or solve ID idempotent when the stored fields match. A scramble/puzzle mismatch is refused before saving. The existing save order remains session lookup/create, scramble insert, then solve insert; a partial insert can therefore exist, but retry repeats the same identities and values.

The owner ID is captured at run start. A guest completion does not write automatically, even if Auth becomes signed in during the run. The user may explicitly retry while signed in to associate that still-unowned guest completion with the current account; the provider then pins that owner for all later retry steps. Once an owner is captured, a different account cannot adopt the pending solve. For signed-in runs, the provider checks that the captured owner is still the active account after each asynchronous repository step. Session lookup/create, scramble save, and solve save accept the expected owner ID; Supabase adapters reject a current account mismatch before issuing a query and writes continue to supply the captured owner ID for RLS enforcement. Route navigation does not discard the provider state. Unsaved work remains in memory only and is guarded by the existing before-unload warning; reload or tab closure can still lose an unconfirmed save.

The timer does not add penalty controls. The completion retains the existing `NONE`, `PLUS_TWO`, or `DNF` value, and the existing penalty repository operation updates only the penalty column, leaving solve and scramble identity unchanged. No schema migration was made. The current schema persists generator version but not provider or generation method; Phase 05 must add and verify those columns before claiming that provenance survives reload. These guarantees are covered by the timer integration and repository tests; browser navigation and live Supabase/RLS transitions were not exercised against a hosted project.

## Phase 05 Supabase scramble provenance

The existing `public.scrambles` table already enforces owner-only RLS, immutable rows, owner/puzzle uniqueness for solve foreign keys, and an owner-created index. Its existing composite foreign keys require every solve to reference a scramble and session owned by the same user with the same puzzle. Phase 05 leaves those policies, grants, constraints, and trigger functions unchanged.

Migration `20261019000100_scramble_generation_provenance.sql` adds nullable `generator_provider` and `generation_method` columns. Provider values must be nonblank and at most 128 characters when present; method accepts `RANDOM_STATE` or `RANDOM_MOVE` when present. Existing rows remain NULL because their original provider and method cannot be established safely. No backfill is performed. New writes from the current generator persist `cubing.js`, its pinned version, and the event's actual method. The typed repository read maps SQL NULL provenance to absent optional domain properties, and returns exact notation as stored. Reads are owner-filtered in the adapter and remain covered by the database's existing RLS.

Scramble retries remain idempotent by stable UUID. A duplicate ID is accepted only when owner-visible puzzle, exact notation, provider, generator version, method, and timestamp all match the retry; differing metadata is returned as an error. The immutable database trigger prevents changing any provenance after insertion. A scramble inserted before a failed solve insert remains an unconfirmed partial row; retry uses the captured scramble and solve identities from the same in-memory completion.

**Migration and deployment order:** review and approve migration `20261019000100_scramble_generation_provenance.sql`, then apply it to the target Supabase project before deploying a client build that selects or writes the new columns. The migration is additive and forward-only. Rollback is to restore the prior client build; do not drop the columns because clients or later rows may already depend on them. Hosted migration application is pending and was not performed in this phase. After approval and hosted application, verify the migration history, both nullable columns and their constraints, that old rows remain NULL, and owner-only read/insert plus immutable-row behavior using two test accounts. The local SQL suite covers metadata constraints/immutability and owner isolation (`03_scramble_provenance.test.sql`, `04_scramble_provenance_rls.test.sql`) alongside the existing integrity and access-denied suites. Run `supabase test db` after a local Supabase stack is available; no hosted database is a valid test target.

**Specification resolution:** older Category 03 source documents describe IndexedDB and offline-first persistence. The Phase 05 authority and newer Category 02A/master Supabase-only decision supersede those persistence directions. Scramble generation and timing remain client-side, but a solve is durably saved only after Supabase confirms it; failed work remains in memory and is not represented as saved history.

## Phase 06 saved history and failed-write UX

**History semantics:** history contains a scramble only when a server-confirmed `solves` row links to it. This follows the current timer write lifecycle (`session` → immutable `scramble` → `solve`) and avoids background uploads for every generated scramble. A scramble inserted before a failed solve insert is a partial, unconfirmed row and does not appear in history. Generated-but-unused scrambles remain ephemeral in the timer view; a guest can still generate and time without Supabase. Unsaved completion retry remains manual, in memory, and reuses the existing solve and scramble IDs. Reload or tab closure can still lose an unconfirmed completion.

**Query and paging:** the repository first queries the authenticated owner's `solves`, explicitly filters `owner_id` and optional puzzle/date bounds, and orders by `created_at DESC, id DESC`. Each request is limited to at most 51 solve rows (50 visible plus one look-ahead); the default UI page is 25. The continuation cursor is the last visible solve timestamp and UUID, with a lexicographic keyset predicate for timestamp ties. It then loads only those page's linked scrambles, explicitly filters the same owner, and preserves solve order. The adapter checks the authenticated account before reading and again around the linked-row read. Client filter request IDs suppress stale responses, account changes immediately hide data from the prior owner, and append logic deduplicates solve IDs. Dates filter the available solve `created_at`; no origin field exists, so there is no origin filter.

**Display and active timer boundary:** `/scrambles` is separate from `/timer`, and the route does not use or update `TimerCompletionProvider`. It shows the exact stored notation, saved-with-solve status, solve save time, and available provider/version/method. Legacy NULL provenance is labeled unknown. Copy writes the original notation string and reports clipboard errors. Replay/reuse is deferred because moving a historical record into the timer's immutable scramble lifecycle needs a separately reviewed flow; viewing and copying have no timer side effect. The guest view explains that saved history requires sign-in while guest scramble generation remains available on the timer.

**Schema compatibility and deployment:** history reads and scramble inserts recognize only PostgreSQL `42703` or PostgREST `PGRST204` errors that explicitly name `generator_provider` or `generation_method` on `scrambles`. History retries once with the pre-migration select. A scramble insert retries once with the pre-migration insert payload, retaining the same owner, UUID, puzzle, exact notation, generator version, and timestamp. RLS, authentication, network, foreign-key, and unrelated schema errors do not trigger fallback. On the legacy schema, provider and generation method remain in the in-memory completion snapshot but cannot be durably stored. A legacy duplicate-ID retry is accepted only when the owner-visible stored owner, puzzle, exact notation, generator version, and timestamp match. Apply and verify `20261019000100_scramble_generation_provenance.sql` in the target project before deploying a client that depends on durable provenance. Do not connect to hosted Supabase or apply that migration as part of this phase.

**Verification status and limits:** focused UI and repository tests cover owner scope, mismatched accounts, legacy NULL provenance, keyset tie predicates, page bounds, puzzle/date filters, empty/error/retry, stale filter responses, account changes, exact copy, and no timer-state mutation. Existing timer retry coverage protects stable IDs and manual retry. The local SQL/RLS suite remains unexecuted: Phase 05 found no PostgreSQL listener at `127.0.0.1:54322` and Docker API access was denied; in Phase 06 the local TCP probe again failed and the `supabase` executable was not on the current PATH. No SQL/RLS pass is claimed. Hosted RLS remains a deployment prerequisite for review using separate test accounts after the approved migration is applied.

## Solve-save compatibility correction

The core history migration defines `scrambles` without `generator_provider` or `generation_method`. Phase 05's repository started writing both columns, while migration `20261019000100_scramble_generation_provenance.sql` has not yet been applied to the hosted project. Against that pre-migration schema, PostgREST reports `PGRST204` or PostgreSQL reports `42703`; the previous write path returned the generic cloud failure. This schema mismatch is confirmed from the deployed-migration status and local payload/schema comparison. Live hosted save behavior was not tested.

The repository first attempts the modern insert with both provenance fields. It retries once using legacy columns only when the server error explicitly identifies one of those two columns on `scrambles`. The retry reuses the exact immutable scramble identity and does not regenerate notation or IDs. Other errors, including authentication, RLS/permission, network, foreign-key, and unrelated missing-column failures, are returned without retry. If a legacy retry hits a duplicate UUID, the adapter accepts it only after owner-scoped data comparison against all fields the legacy schema can store. Provider and method stay in the pending in-memory scramble snapshot but are temporarily not persisted on this schema; they become durable only after the migration is applied.

Deployment order is: apply and verify the additive provenance migration in the target Supabase project, then deploy the client. Once every supported environment has the migration and the minimum supported database schema guarantees both columns, remove the legacy insert retry and its compatibility tests in a separately reviewed change. Until local PostgreSQL/RLS tests and authorized hosted verification are run, this behavior is covered by deterministic repository mocks only; database policy and live cloud save success are not claimed.
