# RubiVision AI — Scrambles/Cube — Prompt 05/12

## PROMPT 05 — Scramble notation parsing, normalization policy and inverse correctness
**Agent instruction:** Implement notation validation and utilities using a verified parser; do not implement an incomplete cube move grammar that accepts impossible puzzle moves.

**Steps:**
1. Enumerate notation supported for each puzzle, including face turns, primes, double turns, and larger-cube wide turns/numbered layers where generated by the selected library.
2. Use the library parser when possible. Separate syntactic parseability from puzzle legality: a syntactically valid move may be inappropriate for a specific puzzle.
3. Reject unsupported symbols, invalid layer widths, empty sequences, and malformed tokens; provide useful error messages.
4. Keep display notation exactly aligned with the generated/stored scramble. Any formatting or token highlighting must not change underlying text.
5. Provide an inverse-algorithm utility using the same library's algorithm representation. Avoid naive string reversal or manually replacing apostrophes.
6. Verify state identity after applying a sequence followed by its inverse on each puzzle **only when a reliable puzzle-state engine is available**; otherwise record the test as deferred to Prompt 09, not passed.
7. Ensure long sequences remain readable and do not cause UI overflow.

**Suggested files:** `features/scramble/scrambleParser.ts`, `scrambleNotation.ts`, `scrambleParser.test.ts`.

**Tests:** standard 3×3 notation; 4×4–7×7 wide/layer examples from the actual generator; invalid tokens; puzzle mismatch; inverse of single/multi-move algorithms; exact text preservation.

**Acceptance:** Every emitted scramble is accepted by the same verified grammar and no unsupported notation is silently accepted.

### Canonical contracts and invariants
Use existing shared types if present; otherwise coordinate these contracts with the foundation module:

```ts
export type PuzzleType = '222' | '333' | '444' | '555' | '666' | '777';
export interface Scramble {
  id: string;              // stable UUID
  puzzle: PuzzleType;
  notation: string;        // exact displayed sequence, never silently rewritten
  generatorVersion: string;// identifiable library/algorithm version
  createdAt: string;       // ISO 8601 UTC
}
export interface ScrambleService {
  generate(puzzle: PuzzleType): Promise<Scramble>;
}
```

A solve references one immutable `scrambleId`, and its puzzle matches the scramble puzzle. The currently visible scramble must be captured at solve start and must not change until the solve is safely completed/aborted according to timer rules. Generation can be async; stale results must never replace a newer request. A viewer failure cannot prevent generating, timing, or saving a solve. Persist scrambles via the storage/repository layer; do not implement an isolated competing persistence system.
